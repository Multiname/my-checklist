## Экран и ассеты
Экран — прокручиваемый на весь экран список категорий (`ft.ListView`) и
`button_area` в правом нижнем углу. При запуске категории и их пункты
загружаются из БД в порядке `position`; пустой список — пустой экран.
Каждая категория показывает свои пункты внутри панели, под названием
(см. [Design.md](Design.md), «Пункт»). `create_category`,
`rename_category` и `delete_category` работают; кнопки переименования и удаления
показываются при выделенной категории (а при выделенном пункте на их месте —
кнопки пункта).

Перетаскивание категорий реализовано на задаче 4 этапа 2 — см.
«Перетаскивание категорий», переименование — на задаче 5, см.
«Переименование категории», удаление — на задаче 6, см.
«Удаление категории».
Добавление пунктов с вводом названия реализовано на задаче 2 этапа 3 — см.
«Добавление пункта». Выделение пунктов — на задаче 3 этапа 3, см. «Выделение
пункта»: пункт выделяется долгим нажатием или тапом внутри выделенной
категории, и в `button_area` при этом показываются кнопки пункта. Перетаскивание
пунктов — на задаче 4 этапа 3, см. «Перетаскивание пунктов», переименование
пункта — на задаче 5 этапа 3, см. «Переименование пункта», удаление — на
задаче 6, см. «Удаление пункта».

Пока идёт ввод названия (категории или пункта), `button_area` скрыта: кнопки не поднимаются
вместе с содержимым при появлении клавиатуры и не мешают вводу. Так же
контейнер скрыт всё время, пока перетаскивается категория или пункт, — см.
«Перетаскивание категорий» и «Перетаскивание пунктов».

`create_category` (`ChecklistApp.create_category`): в БД добавляется категория с
названием «Категория» (`position` = конец списка), панель добавляется в конец
списка, затем название заменяется на `TextField` с `autofocus` — открывается
клавиатура. Ввод начинается в `_begin_title_input()`: там же скрывается
`button_area`. Ввод завершается по кнопке действия клавиатуры, тапу вне поля,
потере фокуса, скрытию клавиатуры (`on_submit`/`on_tap_outside`/`on_blur` плюс
`page.on_media_change`) и кнопке/жесту «назад» (см. «Переименование категории»);
пустой ввод сохраняется как «Категория» (`normalize_title`). Название пишется
в БД до обновления панели: при ошибке записи экран остаётся прежним,
показывается `SnackBar`. После завершения ввода (`_finish_title_input()`) на
панели снова текст, а `button_area` возвращается в правый нижний угол.

`create_title_input()` — общий шаблон поля ввода названия (категории и
пункта): `value` задаёт начальный текст (при переименовании — прежнее
название), `on_commit` — завершение ввода, `on_tap_outside` — отдельный
обработчик тапа вне поля; стиль текста и подсказку передаёт вызывающий.
`create_category_input()` и `create_item_input()` подставляют стили категории и
пункта. `_start_title_input()` показывает поле, для новой
категории сначала прокручивает список к концу (`scroll_to(offset=-1)`), затем
передаёт полю фокус (`await field.focus()`). Переименовываемая категория уже на
экране: её выделяли, а поле в фокусе Flutter сам показывает на экране; так же
показывается и поле нового пункта.

Скрытие клавиатуры — отдельный сигнал, потому что жест «назад» на Android
закрывает её, не снимая фокус с поля и не присылая `on_blur`. При `adjustResize`
высота клавиатуры не попадает в `view_insets` (Flutter отдаёт нули), поэтому
`ChecklistApp._keyboard_visible()` считает клавиатуру открытой, если пропал
нижний системный padding навигации (`media.padding.bottom == 0`); состояние
отслеживается по `page.on_media_change`. Ограничение: на устройствах, где
нижний padding всегда 0 (edge-to-edge без панели навигации), этого сигнала нет,
но ввод всё равно завершается тапом вне поля, потерей фокуса и кнопкой
«назад» — пока идёт ввод, она перехватывается (`can_pop = False`) и сохраняет
название (см. `_on_confirm_pop`).

Высота панели при вводе не меняется: текст названия и поле ввода используют
общий `CATEGORY_TITLE_STYLE` с явной межстрочной высотой `1.45`
(`CATEGORY_TITLE_LINE_HEIGHT`), а у поля включён `dense` — иначе `TextField`
выше текста на высоту Material-поля.

`button_area` реализована в `src/main.py`: `icon_button()` — круглая кнопка
с иконкой, `create_button_area(actions)` — контейнер из трёх кнопок-слотов
(плюс, карандаш, корзина), закреплённый свойствами `right`/`bottom` в
`ft.Stack`. Кнопки постоянные, а их действие зависит от выделения — см.
«Кнопки button_area: три переиспользуемых слота». Видимость контейнера
переключает `ChecklistApp` (`button_area.visible`) через `_apply_selection()`:
контейнер скрыт, пока идёт ввод названия или перетаскивание
(`_editing_view`/`_dragging`/`_item_drag`), и возвращается, когда ничего из
этого нет.
Шаблон категории — `create_category_panel()`, список —
`create_category_list()`. Параметры внешнего вида — в [Design.md](Design.md).

### Кнопки button_area: три переиспользуемых слота
Задача 1 этапа 3 добавляет кнопки пунктов. Иконки у пунктов те же, что у
категорий (плюс, карандаш, корзина), а место на экране по спеке не меняется:
кнопка пункта «заменяет» кнопку категории на том же месте
([feature-button-area.md](features/feature-button-area.md)). Поэтому в
`button_area` не шесть кнопок, а те же три слота с постоянной иконкой; при
смене выделения меняется действие слота — подпись для TalkBack, обработчик и
видимость.

- `ButtonAction` — действие слота: `label`, `handler`, `visible`.
  `bind_button(button, action)` записывает их в существующую кнопку,
  `create_button_area(actions)` строит контейнер и требует ровно три действия
  (`ValueError` иначе: `zip` молча обрезал бы список).
- Действия для текущего выделения собирает `ChecklistApp._actions()`, применяет
  `_apply_selection()`; за каждым действием стоит отдельный метод приложения
  (`create_category`, `add_item`, `rename_category`, `delete_category`,
  `rename_item`).

Таблица действий (слоты — сверху вниз):

| Выделение | Плюс | Карандаш | Корзина |
|---|---|---|---|
| нет | `create_category` | скрыта | скрыта |
| категория | `add_item` | `rename_category` | `delete_category` |
| пункт | `create_category` | `rename_item` | `delete_item` |

- **Почему не шесть кнопок.** Второй набор пришлось бы держать скрытым и
  следить, чтобы видимость пар всегда была согласована: один и тот же слот
  задавался бы двумя флагами, и любая правка легко дала бы две видимые кнопки
  на месте. Кроме того, скрытые кнопки не занимают места в `Column`, поэтому
  порядок контролов пришлось бы чередовать (`create_category`, `add_item`,
  `rename_category`, …), и индексы в `controls` перестали бы совпадать со
  слотами. С тремя слотами состояние описывается одной таблицей, а виджетов и
  флагов вдвое меньше.
- **Почему не внутреннее разветвление в одном обработчике.** Тогда действия
  для категории и пункта лежали бы в одном методе, а подпись для TalkBack всё
  равно пришлось бы менять отдельно — состояние «что делает кнопка» оказалось
  бы размазано по двум местам. Сейчас действие — значение таблицы, и каждая
  кнопка по-прежнему вызывает отдельный метод (`create_category`,
  `rename_category`, …), который удобно тестировать.
- **Виджет не пересоздаётся.** Flet разрешает обработчик события на сервере в
  момент события (`Control._trigger_event` → `getattr(control, "on_click")`),
  поэтому новое действие работает сразу, даже если клиент ещё не получил
  патч. Подпись (`Image.semantics_label`) доезжает ближайшим `page.update()`;
  иконка и размеры не меняются, кнопки не мигают и не сдвигаются.
- На задаче 1 этапа 3 обработчик плюса при выделенной категории был заглушкой
  `_no_op`; на задаче 2 этапа 3 он создаёт пункт (см. «Добавление пункта»).
  На задаче 3 этапа 3 в таблицу добавлена третья строка — действия пунктов
  (см. «Выделение пункта»). На задаче 5 этапа 3 обработчик `rename_item`
  переименовывает пункт (см. «Переименование пункта»), на задаче 6 —
  `delete_item` удаляет его (см. «Удаление пункта»): заглушек в таблице больше
  нет.
- При выделенном пункте плюс снова создаёт категорию: категория в этот момент
  не выделена, а `create_category` видна всегда, пока не выделена категория
  ([feature-button-area.md](features/feature-button-area.md)).

### Выделение категории
Выделение реализовано на задаче 3 этапа 2. Выделена может быть только одна
категория — её хранит `ChecklistApp._selected_view`; цвет панели переключает
`CategoryView.set_selected()`, действия и видимость кнопок —
`ChecklistApp._apply_selection()`.

- Выделенным может быть только один элемент — категория или пункт (см.
  «Выделение пункта»): `_select_category()` снимает выделение с пункта
  (`_clear_item_selection()`), `_select_item()` — с категории.
- Долгое нажатие по панели срабатывает по всей её площади, кроме строк пунктов:
  его ловит `GestureDetector` самой категории (`CategoryView.gesture_area`).
  Строка пункта — исключение: у неё свой `GestureDetector`, лежащий глубже в
  дереве, поэтому долгое нажатие по пункту выделяет пункт, а не категорию (см.
  «Выделение пункта»).
- Перетаскивание начинается не тем нажатием, что выделение, а следующим: первое
  долгое нажатие выделяет категорию (палец отпускается), второе долгое нажатие
  по уже выделенной категории её поднимает — см. «Перетаскивание категорий».
  Случайное долгое нажатие поэтому список не двигает.
- Виброотклик — `ft.HapticFeedback` в `page.services`, `medium_impact()`.
  Он даётся на каждое долгое нажатие (`_on_category_long_press()`): и на
  выделение, и на подъём — для пользователя это два разных действия, и оба
  должны чувствоваться.
- Тап снимает выделение: список обёрнут в `ft.GestureDetector`
  (`create_category_area()`). Прокрутка выделение не снимает — жест уходит
  списку. Тап по кнопкам `button_area` до списка не доходит: контейнер лежит
  выше в `Stack`. Тап, которым закрывают клавиатуру (пока идёт ввод названия),
  выделение не снимает.
- «Назад» (кнопка и жест) не закрывает приложение, пока категория выделена:
  корневому представлению (`page.views[0]`) назначается `on_confirm_pop`,
  а `can_pop` в `_apply_selection()` выставляется в `False`. Flutter
  перехватывает «назад» (`PopScope`) и вызывает обработчик, тот снимает
  выделение и отвечает `confirm_pop(False)`. Без выделения `can_pop = True`,
  и «назад» закрывает приложение как обычно.
- Пока открыта клавиатура, первый «назад» закрывает её на уровне Android
  (см. ниже), выделение снимает следующий.
- Пока идёт ввод названия, `can_pop` тоже `False`: «назад» завершает ввод
  (сохраняет название), не закрывая приложение и не снимая выделение — см.
  «Переименование категории».

### Переименование категории
Реализовано на задаче 5 этапа 2. Кнопка `rename_category` привязана к
`ChecklistApp.rename_category()`: у выделенной категории название заменяется
полем ввода на том же месте. Поле создаётся тем же шаблоном, что и при
создании (`create_category_input`), но с `value = view.title` — ввод начинается
с прежнего названия, курсор в конце, а `autofocus` открывает клавиатуру;
`_start_title_input()` передаёт полю фокус и не прокручивает список: категорию
только что выделили на экране, а поле в фокусе Flutter показывает сам.

- Ввод завершается теми же сигналами, что и у новой категории
  (`on_submit`/`on_tap_outside`/`on_blur`/`page.on_media_change`), а также
  кнопкой/жестом «назад»: `_on_confirm_pop()` при активном вводе сначала
  вызывает `_finish_title_input()` и только потом отвечает
  `confirm_pop(False)`.
- Выделение при переименовании не снимается. `_finish_title_input()` его не
  трогает, а `_apply_selection()` возвращает слотам действия текущего
  выделения (`add_item`/`rename_category`/`delete_category`).
- Тап, которым закрывают клавиатуру, выделение тоже не снимает. Нажатие
  приходит в `on_tap_outside` поля раньше, чем отпускание в `on_tap` списка,
  и к моменту `on_tap` ввод уже завершён — без дополнительного признака
  выделение снялось бы. Поэтому обработчик поля выставляет
  `_tap_ended_input`, и `on_tap` того же тапа только сбрасывает флаг. Если
  жест перестал быть тапом (прокрутка), флаг снимает `on_tap_cancel`.
- Неизменённое название в БД не пишется: `_finish_title_input()` сравнивает
  нормализованный ввод с текущим названием (`normalize_title`), а пустой ввод
  даёт «Категория», как и при создании.
- Запись — `Storage.set_category_title()`, до обновления панели: при ошибке
  панель остаётся с прежним названием, показывается `SnackBar`. Новое
  название приходит из БД (нормализованное) и после перезапуска
  восстанавливается вместе с остальными данными.

### Удаление категории
Реализовано на задаче 6 этапа 2. Кнопка `delete_category` привязана к
`ChecklistApp.delete_category()`: выделенная категория удаляется из списка и из
БД. Подтверждения нет — спека требует удаления по нажатию
([feature-category.md](features/feature-category.md)).

- Запись — `Storage.delete_category()`, до обновления экрана: при ошибке
  (нет места, файл только для чтения) список, выделение и кнопки остаются
  прежними, показывается `SnackBar`. Это же правило действует для остальных
  операций ([feature-storage.md](features/feature-storage.md)).
- Пункты удалённой категории отдельно не удаляются: их уносит каскад
  `ON DELETE CASCADE` (правило схемы проверено тестом хранилища; в UI пункты
  появились на задаче 2 этапа 3, а отдельная проверка каскада — задача 7
  этапа 3).
- Хранилище возвращает оставшийся порядок категорий, и приложение применяет его
  (`_apply_category_order()`), как после перетаскивания: `position` оставшихся
  идут `0..n-1` без дыр, то есть хранилище остаётся источником истины.
- Выделение снимается: удалённой категории больше нет, поэтому `_selected_view`
  обнуляется, а `_apply_selection()` возвращает слоты к исходным действиям
  (виден только `create_category`) и `can_pop = True`. Список в памяти и
  `controls` списка обновляет `_remove_view()`.
- Кнопка видна только при выделенной категории, а во время ввода названия и
  перетаскивания `button_area` скрыта целиком — поэтому удалить категорию
  с открытым полем ввода или в середине drag нельзя. На случай такого
  состояния (оно недостижимо через UI) `delete_category()` сбрасывает ввод:
  поле уходит вместе с панелью, а не остаётся у несуществующей категории или
  её пункта (ввод названия пункта тоже сбрасывается).

### Добавление пункта
Реализовано на задаче 2 этапа 3. Кнопка `add_item` привязана к
`ChecklistApp.add_item()`: в выделенной категории появляется новый пункт, и
сразу открывается ввод его названия.

- Шаблон пункта — `create_item_panel()`: `ft.Row` из чекбокса слева и названия
  справа, на прозрачном `ft.Container` (`ITEM_PANEL_COLOR`). Пункт лежит внутри
  панели категории, поэтому сквозь него видна панель — в том числе выделенная.
  Чекбокс показывает `is_checked` из БД; переключение отметки — задача 8 этапа 3.
  Горизонтальный отступ **16** — у самого пункта (`ITEM_PANEL_PADDING`), а не у
  панели: тогда выделенная строка закрашивает панель до краёв (см. «Выделение
  пункта»).
- Жесты пункта — `create_item_row()`: вокруг панели пункта лежит
  `ft.GestureDetector` с `on_long_press` и `on_tap` (см. «Выделение пункта»).
  `ItemView.row` — то, что лежит в контейнере пунктов; `ItemView.panel` —
  панель строки внутри него.
- Пункты категории лежат в её контейнере пунктов — `create_items_box()`, второй
  элемент колонки панели (`create_category_content()`). Пока пунктов нет,
  контейнер скрыт (`visible = False`) и не занимает места, поэтому пустая
  категория выглядит как раньше; отступ от названия — внутренний `padding`
  контейнера, а не `spacing` колонки (иначе он добавился бы и для пустого
  контейнера). `CategoryView.append_item()` добавляет пункт в конец
  `self.items`, в `items_box.content.controls` и показывает контейнер; там же
  пункт получает ссылку на свою категорию (`ItemView.category_view`) и
  обработчики жестов.
- `add_item()` пишет в БД (`Storage.create_item()`) до обновления экрана: при
  ошибке пункт не появляется и показывается `SnackBar`. Затем пункт добавляется
  в конец категории, и открывается поле ввода — то же самое, что у категории:
  поле занимает место названия (`title_slot`), `autofocus` открывает клавиатуру.
  Ввод начинается с пустого значения и подсказки «Пункт»: если ничего не
  ввести, пункт останется «Пункт» (он уже создан с этим названием, и запись не
  повторяется).
- Прокрутки списка при добавлении пункта нет (`scroll_to` не вызывается):
  категория не обязательно последняя, и прокрутка к концу списка увела бы новый
  пункт из вида. Поле в фокусе Flutter показывает на экране сам — это уже
  работает при переименовании категории.
- Ввод названия пункта обслуживает та же машинерия, что и у категории:
  `TitledView` — общая часть `CategoryView` и `ItemView` (название, `title_slot`,
  поле ввода, `show_input()`/`show_title()`, `default_title`, `save_title()`).
  `ChecklistApp._editing_view` теперь `TitledView | None`, поэтому завершение
  ввода по кнопке действия клавиатуры, тапу вне поля, потере фокуса, скрытию
  клавиатуры и «назад» работает для обоих без дублирования. `_finish_title_input()`
  берёт дефолт из `view.default_title`, а запись — из `view.save_title()`
  (`Storage.set_category_title()` или `Storage.set_item_title()`).
- Новое название приходит из БД (нормализованное): при ошибке записи пункт
  остаётся «Пункт», поле уступает место тексту, показывается `SnackBar`
  (как у категории). Выделение категории при создании и вводе пункта не
  снимается; после ввода `button_area` возвращается, `can_pop = False` — ввод
  и выделение обрабатываются как раньше.
- Пункты загружаются при запуске одним запросом `Storage.list_items()`
  (JOIN с категориями, порядок — как у категорий, внутри категории по
  `position`) и раскладываются по категориям в `mount()`. Отметки
  восстанавливаются из БД в чекбоксах.
- Стиль текста пункта меньше, чем у категории; подробности и константы —
  в [Design.md](Design.md), «Пункт».
- «Сворачивание» пунктов при перетаскивании категории (см.
  [feature-category.md](features/feature-category.md)) пока не реализовано —
  пункты остаются видимыми; это отдельная задача.

### Выделение пункта
Реализовано на задаче 3 этапа 3. Выделенным может быть только один элемент:
категорию хранит `ChecklistApp._selected_view`, пункт — `_selected_item`; цвет
строки переключает `ItemView.set_selected()`, действия и видимость кнопок —
`_apply_selection()`.

- Выделить пункт можно двумя способами (см.
  [feature-item.md](features/feature-item.md)): долгим нажатием по нему, когда
  ничего не выделено, или тапом по пункту внутри выделенной категории. В обоих
  случаях `_select_item()` снимает выделение с категории и с прежнего пункта,
  после чего даётся виброотклик `medium_impact()` — как у категории.
- Долгое нажатие по пункту перехватывает сам пункт: каждый пункт обёрнут в
  `ft.GestureDetector` (`create_item_row()`), который лежит внутри области жестов
  категории (`CategoryView.gesture_area`). Распознаватель пункта добавляется в
  арену жестов раньше, и его таймер долгого нажатия (500 мс) срабатывает первым,
  поэтому категория не выделяется и не перетаскивается; на устройстве это
  проверено долгим нажатием по пункту: выделился пункт (розовая строка), а не
  панель. По остальной панели категории (название и отступы) долгое нажатие
  принадлежит категории — это её перетаскивание.
- Тап по пункту обрабатывает `_on_item_tap()`; до списка событие не доходит
  (вложенный `GestureDetector` выигрывает тап в арене), поэтому правила те же:
  внутри выделенной категории тап выделяет пункт, в остальных случаях снимает
  выделение. Тап, которым закрывают клавиатуру, выделение не снимает — флаг
  `_tap_ended_input` работает так же, как у `on_tap` списка.
- Тап по любому месту вне пунктов (`_on_tap`) снимает выделение и с пункта:
  `_deselect()` обнуляет и `_selected_view`, и `_selected_item`.
- «Назад» обрабатывается тем же `_on_confirm_pop()`: при выделенном пункте
  `can_pop = False` (см. `_apply_selection()`), обработчик снимает выделение и
  отвечает `confirm_pop(False)` — приложение не закрывается. Следующая «назад»
  без выделения закрывает его, как обычно.
- Пока идёт ввод названия, тап и долгое нажатие по пункту выделение не меняют
  (тап только завершает ввод): иначе тап, закрывающий клавиатуру, снимал бы
  выделение.
- Фон строки — `ITEM_PANEL_SELECTED_COLOR`, то есть тот же
  `TERTIARY_CONTAINER`, что у выделенной категории. Строка закрашивается во всю
  ширину панели: горизонтальный отступ переехал с панели на сам пункт, поэтому
  ни ширина, ни высота строки при выделении не меняются (на устройстве строка —
  **167** физических px и в обычном, и в выделенном состоянии, панель пустой
  категории по-прежнему **185** физических px).
- Действия пункта (`rename_item`, `delete_item`) появились в таблице на этой
  задаче. На задаче 5 этапа 3 `rename_item` получил обработчик
  (`ChecklistApp.rename_item()`, см. «Переименование пункта»), на задаче 6 —
  `delete_item` (`ChecklistApp.delete_item()`, см. «Удаление пункта»).
- Если удалить категорию, в которой лежит выделенный пункт, выделение пункта
  снимается вместе с панелью. Через UI такое состояние недостижимо (выделение
  взаимоисключающее), но `delete_category()` защищается от рассинхронизации так
  же, как для открытого поля ввода.

### Перетаскивание пунктов
Реализовано на задаче 4 этапа 3. Перетаскивание начинается только у выделенного
пункта, причём следующим долгим нажатием: первое выделяет пункт, палец
отпускается, второе — поднимает его. Жест по невыделенному пункту двигает только
выделение. Отдельного списка внутри категории нет — пункт живёт в контейнере
пунктов панели, а перетаскивать его нужно и в другую категорию, поэтому drag
пункта ведёт сам `ChecklistApp` по событиям жеста.

- Жест пункта — `ft.GestureDetector` (`create_item_row()`, обработчики назначает
  `ItemView`). Долгое нажатие приходит двумя событиями: `on_long_press_start`
  (`_on_item_drag_start()`) и `on_long_press` (`_on_item_long_press()`), который
  выделяет пункт и даёт виброотклик. Подъём начинается только тогда, когда пункт
  уже выделен (`_on_item_drag_start()` сверяется с `_selected_item`): у первого
  долгого нажатия выделения ещё нет, поэтому оно только выделяет, а поднимает
  пункт второе нажатие по нему же. Внутри жеста подъёма `on_long_press_start`
  приходит раньше `on_long_press`, поэтому проверяется выделение, оставшееся от
  прошлого жеста. Движение пальца приходит в `on_long_press_move_update`
  (`_on_item_drag_move()`), отпускание — в `on_long_press_end`
  (`_on_item_drag_end()`).
- Пункт «поднимается» так же, как панель категории: его строка сворачивается
  (`ItemView.collapse()` — высота панели 0, содержимое обрезано), над списком в
  `Stack` появляется её копия (`create_item_proxy()`) — розовая строка того же
  размера с чекбоксом и названием, без тени и подложки. Прокси двигается за
  пальцем (`_move_proxy()`), сохраняя точку захвата: `Stack` лежит ровно над
  областью списка, поэтому его координаты — это координаты модели плюс экранный
  верх содержимого списка. **По горизонтали пункт не едет.** В списке он живёт в
  одном столбце, переставлять его вбок некуда, поэтому у прокси меняется только
  `top`, а `left` выставляется при подъёме и равен `LIST_PADDING` — столбцу
  строки. Так же ведёт себя категория: клиент двигает её копию только вдоль оси
  списка. Движение пальца вбок не переставляет пункт и не сдвигает прокси;
  порог `ITEM_DRAG_THRESHOLD` и место вставки считаются по вертикальному сдвигу
  (раньше прокси уезжал за пальцем вправо-влево и мог уйти за край экрана).
- На месте будущей вставки стоит зазор (`create_item_gap()`) — пустое место на
  **целый слот пункта**, то есть строку вместе с промежутком после неё
  (`item_slot_height()`): столько занимает ячейка строки, поэтому пункт встаёт на
  место зазора без сдвига остальных строк. Зазор лежит в контейнере пунктов
  целевой категории (`CategoryView.place_gap()`), а
  `CategoryView.remove_gap()` возвращает контейнеру обычный вид.
- Промежуток между пунктами принадлежит ячейке строки (`create_item_cell()`), а
  не `spacing` колонки: свёрнутая при перетаскивании строка остаётся в контейнере
  нулевой высоты, и промежуток вокруг неё давал бы панели лишнюю высоту — остаток
  на месте пункта. Ячейка сворачивается вместе со строкой (`ItemView.collapse()`
  снимает и высоту панели, и отступ ячейки), а нижний отступ панели категории на
  время, пока в контейнере есть что показывать, меньше на этот промежуток
  (`category_panel_padding()`). Поэтому высота панели не меняется ни в первый миг
  перетаскивания, ни после переноса пункта в другую категорию: исходная панель
  сразу равна категории без этого пункта и после отпускания не «сжимается». Если
  в категории не осталось ничего видимого (уносят единственный пункт), контейнер
  пунктов не несёт и отступа от названия — панель выглядит как у категории без
  пунктов. Раньше зазор был высотой строки, а промежуток задавался `spacing`
  колонки: свёрнутая строка оставляла лишний промежуток, панель в первый же миг
  перетаскивания подрастала на 14 физических px, а после переноса в другую
  категорию там оставался «остаток» пункта.
- Сервер не знает координат контролов, поэтому раскладка собирается из высот,
  которые клиент присылает событием `size_change`: у строки пункта
  (`ItemView.height`/`width`) и у названия категории
  (`CategoryView.title_height`). `build_drag_spans()` строит по ним
  `DragSpan`/`DragEntry` — границы панелей, строк и зазора. Клиент присылает
  размеры только для того, что реально разложено, поэтому строки за пределами
  экрана высоты не имеют: `_item_metrics()` берёт измеренные значения как есть,
  а для невидимых строк — среднее измеренное (оценка не влияет на место под
  пальцем: рядом с пальцем всё видно и измерено). `base_row_top()` и точка
  нажатия (`row_global_top - local_position.y`) дают экранный верх содержимого
  списка, поэтому прокрутка списка до начала drag не мешает. По горизонтали
  привязка не нужна: раскладка одномерная (столбец у всех строк один), а прокси
  встаёт в этот столбец при подъёме.
- `drag_slot_at()` переводит координату пальца в пару «категория, номер строки
  среди оставшихся»: выше середины строки — вставка перед ней, ниже — за ней; на
  названии категории — в начало, ниже последней строки — в конец. Промежутки
  между панелями и отступы списка принадлежат ближайшей категории. Раскладка
  каждый раз строится **от текущего зазора**, то есть палец сравнивается со
  строками так, как они видны на экране; это же убирает «дрожание» цели: когда
  зазор переезжает, строка под пальцем не пересекает его середину обратно
  (проверено тестом на отсутствие осцилляции).
- Пока клиент не прислал размеры нажатой строки (например, сразу после
  запуска), долгое нажатие только выделяет пункт, даже когда он уже выделен:
  без её высоты нельзя ни свернуть строку, ни построить прокси.
- Цель пересчитывается на каждом движении (`_update_drag_target()`), а экран
  обновляется каждый раз — прокси должен идти за пальцем (это одно свойство
  `top` у одного контрола; `left` при перетаскивании не меняется). В начале drag
  есть порог `ITEM_DRAG_THRESHOLD` = 8 логических px по вертикали: дрожание
  пальца на месте не считается перетаскиванием и не показывает зазор.
- Автопрокрутка: когда палец ближе `AUTOSCROLL_EDGE` = 48 px к верхней или
  нижней границе видимой области списка, список прокручивается сам. Прокручивает
  его **клиент**: сервер заказывает один анимированный проход до края
  (`_scroll_to_edge()`), длительность которого считается по оставшемуся пути
  (`AUTOSCROLL_SPEED` = 700 px/с). Позиция идёт кадрами клиента (60 fps) и не
  зависит от задержки связи, а не рывками: раньше шаг 12 px заказывался раз в
  40 мс, и каждый запрос ждал ответа клиента — прокрутка получалась дёрганой.
  Цель прохода абсолютная (`offset=-1` — конец списка, `0` — начало), поэтому
  клиент берёт **точный** край: список не уезжает за него и не пружинит обратно.
  Раньше лишний шаг у границы (прокручивать было уже некуда) давал именно такую
  пружину — прокрутка у края списка дёргалась.
- Прокси при автопрокрутке остаётся под пальцем, а место вставки пересчитывается
  по событиям `on_scroll` (`_on_scroll()`): содержимое уезжает под пальцем,
  поэтому зазор переезжает вместе с ним. Из событий же берутся размеры прокрутки
  (`max_scroll_extent`) и высота видимой области. Направление, запуск и остановку
  прохода обновляет `_update_autoscroll()`; номер запуска (`epoch`) отменяет
  прошлый проход, а `_cancel_scroll()` (один `scroll_to(delta=0)`) останавливает
  анимацию в клиенте, когда палец ушёл из зоны или пункт отпущен.
- Остаток до края (`_autoscroll_distance()`) нужен только для длительности: вниз
  он берётся как большее из измеренного и оценённого по раскладке (измеренное
  могло устареть, если список вырос без прокрутки, а оценить меньше края — значит
  не доехать до него). У самого края проход не заказывается вовсе
  (`AUTOSCROLL_REST` = 0,5 px).
- Продолжение прохода по событию `end` — только если **конец списка уехал вниз**:
  за время прохода зазор переезжал, и высота списка менялась. Признак — рост
  `max_scroll_extent` относительно значения на начале этого же прохода
  (`drag.pass_extent`, `AUTOSCROLL_EXTENT_EPS` = 1 px), а не остаток «до края»:
  остаток положителен и тогда, когда список просто увели от края, и по нему
  прокрутка гналась бы за пальцем обратно к концу списка.
- **Строка не должна исчезать из дерева, пока её ведут.** Ленивый список
  (`ft.ListView`) держит в дереве только то, что попадает в его кеш
  (по умолчанию ~250 px за краем экрана), остальное уничтожает. Длинный проход
  автопрокрутки уводит исходную строку за пределы кеша, её `GestureDetector`
  уничтожается вместе с распознавателем, и тот молча перестаёт присылать
  `on_long_press_move_update` и `on_long_press_end`: прокси замирал там, где его
  застал проход, отпускание пальца не обрабатывалось, а список оставался с
  включённой автопрокруткой. Поэтому на время перетаскивания — и пункта, и
  категории — кеш списка растягивается на всё содержимое
  (`_drag_cache_extent()`: `cache_extent` — удвоенная сумма высоты содержимого и
  видимой области; высоты дальних строк оценочные), а после отпускания
  возвращается в `None`. Цена — один разовый кадр, в котором строятся все
  категории (заодно приходят их настоящие высоты); на видимый список и на
  прокрутку это не влияет.
- Пользовательская прокрутка списка (событие `user`) во время перетаскивания
  означает, что жест уже потерян: пока он жив, список двигает только
  автопрокрутка. Тогда перетаскивание снимается (`_finish_active_drag()` без
  записи в БД), иначе прокси висел бы поверх списка до первого тапа, а
  автопрокрутка возвращала бы список к краю.
- Зона выхода из автопрокрутки шире зоны входа на `AUTOSCROLL_HYSTERESIS` =
  16 px: палец, стоящий на самой границе, не должен выключать и снова включать
  прокрутку дрожанием в пиксель.
- Если за проход высота списка изменилась (зазор переезжал), цель прохода может
  оказаться на пару пикселей за новым краем: клиент упирается в край и стоит
  там до конца прохода, движения за край нет. Видно это только как одно
  событие `overscroll`; на экране ничего не меняется — проверено кадрами.
- Пока пункт перетаскивается, `button_area` скрыта целиком — как при
  перетаскивании категории (см. `_apply_selection()`). Выделение и кнопки
  пункта после отпускания остаются.
- Отпускание: `_finish_item_drag()` убирает прокси, зазор и возвращает строке
  высоту, после чего вызывается `Storage.move_item()` с номером строки среди
  оставшихся (это уже позиция «после удаления перемещаемого пункта», как у
  `move_category`). Хранилище возвращает порядок прежней и новой категории, а
  `_apply_item_orders()` раскладывает пункты по панелям. Хранилище — источник
  истины, как и у категорий. Строки пунктов не пересоздаются: они переезжают
  между контейнерами как есть (клиент сопоставляет контролы по id), поэтому
  отметки, размеры и выделение сохраняются. Если из категории уехал последний
  пункт, её контейнер пунктов снова скрывается и панель уменьшается.
- Ошибка записи — `SnackBar` «Не удалось переместить пункт», порядок в памяти и
  на экране остаётся прежним (запись идёт до обновления списка, как у остальных
  операций).
- Перетаскивание в ту же позицию, а также долгое нажатие без движения в БД не
  пишут: цель совпадает с текущей, и `move_item` не вызывается.
- Если жест прерван и `on_long_press_end` не пришёл, прокси и скрытые кнопки
  снимает первый же тап (`_on_tap`/`_on_item_tap` через `_end_drag()` →
  `_finish_item_drag()`) или `on_long_press_cancel`.
- **Свёртка — только под `GestureDetector`.** Высота меняется у панели строки
  (`ItemView.panel`), а не у обёртки над `GestureDetector`: при изменении высоты
  Flet меняет структуру виджетов, и обёртка над распознавателем пересоздала бы
  его — жест обрывался бы на первом же обновлении экрана (на устройстве это
  выглядело так: `on_long_press_start` и `on_long_press` приходят, а
  `on_long_press_move_update` и `on_long_press_end` уже нет). Тест на это
  косвенно страхует структура `ItemView` (слота над строкой нет). У категории
  по той же причине `GestureDetector` лежит **над** панелью
  (`CategoryView.gesture_area`), а сворачивается панель под ним: проверено на
  устройстве — с распознавателем внутри панели drag обрывался после первого
  движения.
- Обход ошибки flet 1.1.2: клиент присылает `offset_from_origin` под именем
  `ofo`, а `LongPressMoveUpdateEvent` ждёт `of`, и разбор события падает с
  `TypeError` (проверено на устройстве). `_patch_long_press_move_event()`
  подставляет нулевое смещение при создании события; обработчику нужны только
  `local_position`/`global_position`. Патч можно убрать, когда ошибка исправлена
  в flet.
- Перетаскивание категорий устроено так же, как у пункта, и тоже ведёт
  приложение — см. «Перетаскивание категорий».

### Переименование пункта
Реализовано на задаче 5 этапа 3. Кнопка `rename_item` привязана к
`ChecklistApp.rename_item()`: у выделенного пункта название заменяется полем
ввода на том же месте — справа от чекбокса, внутри строки пункта. Поле создаёт
`ItemView.create_input()` (`create_item_input()`) — тот же шаблон, что и у
категории, только со стилем названия пункта; `value = view.title`, поэтому ввод
начинается с прежнего названия, а `autofocus` открывает клавиатуру.

- Ввод обслуживает общая машинерия `TitledView` (см. «Добавление пункта»):
  завершение по кнопке действия клавиатуры, тапу вне поля, потере фокуса,
  скрытию клавиатуры (`on_submit`/`on_tap_outside`/`on_blur` плюс
  `page.on_media_change`) и по кнопке/жесту «назад» (`_on_confirm_pop()` сначала
  вызывает `_finish_title_input()` и только потом отвечает
  `confirm_pop(False)`). Ни один из этих сигналов не снимает выделение пункта.
- `_finish_title_input()` сравнивает нормализованный ввод с текущим названием:
  неизменённое название в БД не пишется, пустой ввод сохраняется как «Пункт».
  Запись — `Storage.set_item_title()` до обновления строки: при ошибке строка
  остаётся с прежним названием, показывается `SnackBar`.
- Тап, которым закрывают клавиатуру, выделение тоже не снимает: обработчик
  `on_tap_outside` поля выставляет `_tap_ended_input`, и тап списка или пункта
  только сбрасывает флаг (см. «Переименование категории»).
- После ввода `button_area` возвращается, и в слотах остаются действия пункта
  (`create_category`/`rename_item`/`delete_item`): `_apply_selection()` берёт их
  из `_actions()` по текущему `_selected_item`.
- Новое название приходит из БД (нормализованное) и после перезапуска
  восстанавливается вместе с остальными данными: `mount()` читает пункты
  `Storage.list_items()`.
- Поле занимает место названия внутри строки (`title_slot.expand = True`), а
  высота строки при вводе не меняется: у текста и поля общий `ITEM_TITLE_STYLE`
  с явной межстрочной высотой `1.45`, а у поля включён `dense` (см.
  [Design.md](Design.md), «Пункт»).

### Удаление пункта
Реализовано на задаче 6 этапа 3. Кнопка `delete_item` привязана к
`ChecklistApp.delete_item()`: выделенный пункт удаляется из списка и из БД.
Подтверждения нет — спека требует удаления по нажатию
([feature-item.md](features/feature-item.md)).

- Запись — `Storage.delete_item()`: удаляет строку, материализует позиции
  оставшихся пунктов категории и возвращает их порядок — он и есть источник
  истины, как после `move_item`. При ошибке (нет места, файл только для чтения)
  строка, выделение и кнопки остаются прежними, показывается `SnackBar`; это же
  правило действует для остальных операций
  ([feature-storage.md](features/feature-storage.md)).
- Оставшийся порядок применяет `_apply_item_orders()` — тот же путь, что после
  перетаскивания пункта: строки пунктов не пересоздаются, поэтому их размеры и
  отметки сохраняются, а `position` в БД остаётся без дыр.
- Выделение снимается: удалённого пункта больше нет, поэтому
  `_selected_item = None`, а `_apply_selection()` возвращает слоты к исходным
  действиям (виден только `create_category`) и `can_pop = True`.
- Если удалён последний пункт категории, её контейнер пунктов снова скрывается,
  и панель выглядит как у категории без пунктов (`_sync_items_box()`).
- Кнопка видна только при выделенном пункте, а во время ввода названия и
  перетаскивания `button_area` скрыта целиком — поэтому удалить пункт с
  открытым полем ввода или в середине drag нельзя. На случай такого состояния
  (оно недостижимо через UI) `delete_item()` сбрасывает ввод: поле уходит вместе
  со строкой, а не остаётся фокусом у несуществующего пункта.

### Перетаскивание категорий
Реализовано на задаче 4 этапа 2. Список — `ft.ListView` (`create_category_list()`),
категории лежат в его `controls` элементами `CategoryView.item` — обёртка
`create_category_item()` вокруг `GestureDetector` категории
(`CategoryView.gesture_area`), внутри которого панель.

- Перетаскивание начинается только у **выделенной** категории, и это **второе**
  долгое нажатие (стандартная задержка ≈500 мс): первое выделяет категорию,
  палец отпускается, второе по ней же присылает `on_long_press_start`, и панель
  «поднимается». Нажатие по невыделенной категории поднимает только выделение —
  список при этом не двигается. Чужое выделение тоже не помогает: поднимается
  именно та категория, по которой нажали, и только если она выделена
  (`_on_category_drag_start()` сверяется с `_selected_view`). Долгое нажатие по
  строке пункта выигрывает пункт: его распознаватель лежит глубже в дереве и
  попадает в арену жестов раньше (проверено на устройстве).
- Выделение и перетаскивание — два разных жеста: `on_long_press`
  (`_on_category_long_press()`) выделяет категорию (цвет, виброотклик, кнопки),
  `on_long_press_start` (`_on_category_drag_start()`) следующего нажатия
  поднимает её. Внутри жеста подъёма это событие приходит раньше
  `on_long_press`, поэтому проверяется выделение, оставшееся от прошлого жеста.
- Панель сворачивается (`CategoryView.collapse()` — высота панели 0, отступ
  обёртки снят), а на месте будущей вставки `_place_category_gap()` ставит
  зазор — **`margin` того элемента списка**, перед которым категория встанет
  (или нижний отступ последнего, если место — конец списка). Элементы списка при
  этом не переставляются и не пересоздаются: иначе клиент пересоздал бы
  распознаватель жеста, и drag оборвался бы на первом же обновлении экрана.
  Высота зазора — целый слот категории, панель вместе с промежутком до следующей
  (`CategoryDrag.slot_height`), поэтому остальные категории не сдвигаются ни в
  первый миг перетаскивания, ни после отпускания.
- Пока категория «в руке», над списком в `Stack` лежит её прокси
  (`create_category_proxy()`): та же панель в цвете выделения, с названием и
  пунктами, без тени и подложки. Прокси двигается за пальцем только по вертикали
  и сохраняет точку захвата; `left` у него — столбец списка (`LIST_PADDING`),
  ширина — измеренная ширина панели.
- Пока категория перетаскивается, `button_area` скрыта целиком (на время drag
  выставляется `_dragging = True`, `_apply_selection()` скрывает контейнер так
  же, как во время ввода названия — см.
  [feature-button-area.md](features/feature-button-area.md)), а список держит в
  дереве всё содержимое (`cache_extent`): прокрутка увела бы поднятую панель за
  пределы кеша, ленивый список уничтожил бы её виджет вместе с распознавателем,
  и жест бы оборвался.
- Место вставки считается по модели: `_category_slot_heights()` собирает высоты
  слотов из измеренных панелей (`CategoryView.height`) и шаблона для невидимых
  (`category_panel_height()`), `build_category_spans()` ставит зазор на текущее
  место, `category_span_at()` переводит координату пальца в номер места по
  серединам панелей. Перестановка начинается, когда палец проходит половину
  панели, а раскладка каждый раз строится от текущего зазора — поэтому зазор не
  дрожит, когда палец стоит в нём.
- Новый порядок сохраняет `_on_category_drag_end()`: отпускание уточняет цель,
  затем вызывается `Storage.move_category()` (позиция — номер среди оставшихся
  категорий, то есть место в списке после удаления перемещаемой), а порядок из
  БД применяется к `views` (`_apply_category_order()`), то есть хранилище
  остаётся источником истины. Ошибка записи — `SnackBar`, порядок в памяти и на
  экране остаётся прежним. Если место не изменилось, записи нет.
- Перетаскивание без движения и отмена жеста (`on_long_press_cancel`) прокси и
  зазор убирают, порядок не меняется; общий выход — `_finish_category_drag()`
  (его же вызывают тап после потерянного жеста и `_end_drag()`).
- «Сворачивание» пунктов при перетаскивании (см.
  [feature-category.md](features/feature-category.md)) пока не реализовано:
  при перетаскивании категории её пункты остаются видимыми в прокси — это
  отдельная задача.

#### Автопрокрутка по названию
Раньше перетаскивание категорий вёл `ReorderableListView`, и автопрокрутку
включал **весь прямоугольник** перетаскиваемой категории (`_dragTargetRect` во
Flutter). У длинной категории он выходит за край экрана сразу, поэтому список
начинал ехать в первый же миг перетаскивания. В Flet это не настраивается: у
`ReorderableListView` есть только `auto_scroller_velocity_scalar`. Поэтому
перетаскивание категорий приложение ведёт само, а зона автопрокрутки считается
по **полосе названия** — `CategoryDrag.title_span()`: экранные верх и низ
названия поднятой панели (верх панели плюс её верхний отступ и высота названия).
Дальше действуют те же правила, что и у пункта: зона `AUTOSCROLL_EDGE` = 48 px у
верхней и нижней границы видимой области списка, выход из зоны на
`AUTOSCROLL_HYSTERESIS` = 16 px дальше, один анимированный проход до края списка
со скоростью `AUTOSCROLL_SPEED` = 700 px/с, продолжение прохода только если
список за проход вырос, и остановка `scroll_to(delta=0)`. Пока название в
середине экрана, длинная категория список не двигает — даже если её низ далеко
за экраном.

Ассеты — `src/assets`; `flet run` и `flet build` ищут каталог `assets`
относительно `main.py`, поэтому в коде пути указываются от него:
`ft.Image(src="icons/plus-sign.webp")`. Тест `tests/test_main.py` проверяет,
что файлы иконок на месте.

`org = "com.example"` в `[tool.flet]` — заглушка для Android-идентификатора
приложения; её нужно заменить до сборки APK.

## Хранение данных
Слой — `src/storage.py`, правила схемы и операций —
[features/feature-storage.md](features/feature-storage.md).

- Файл `app.db` лежит в каталоге данных приложения: `FLET_APP_STORAGE_DATA`
  выставляет клиент Flet (на Android — `files/data` во внутреннем хранилище
  приложения, в `flet run` — `.flet/storage/data`). Если переменной нет (прямой
  запуск Python), используется текущий каталог — в собранном приложении это тот
  же каталог данных.
- Схема v1: `meta`, `categories`, `items`; версия хранится в
  `meta.schema_version`, миграции применяются по одной транзакции.
  `schema_version` больше ожидаемой — `SchemaTooNewError`, приложение
  показывает ошибку и не работает с такой БД.
- `open_storage()` на каждом соединении включает `foreign_keys`, `busy_timeout`
  и WAL; после открытия и после каждой изменяющей операции порядок
  `position` материализуется заново (`0..n-1`) — у категорий по всему списку,
  у пунктов в пределах каждой категории (`_materialize_item_positions()`).
- Повреждённый файл БД переименовывается в `app.db.corrupt-<timestamp>`
  (вместе с `-wal`/`-shm`), создаётся пустая БД, пользователю показывается
  сообщение о потере данных; путь к копии — `Storage.recovered_backup`.
- `Storage` синхронный: вызывается из `asyncio.to_thread`, поэтому соединение
  открыто с `check_same_thread=False`, а операции сериализуются
  `threading.Lock`.
- `Storage.delete_category(category_id)` удаляет категорию (пункты — каскадом),
  материализует порядок оставшихся и возвращает его списком `Category`; приложение
  применяет возвращённый порядок к `views`. Неизвестный `id` — `StorageError`,
  БД при этом не меняется (транзакция откатывается).
- `Storage.move_category(category_id, new_position)` переставляет категорию
  (позиция — индекс в списке после удаления перемещаемой, вне диапазона
  подрезается), материализует порядок и возвращает новый список `Category`.
  Приложение применяет возвращённый порядок к `views` — хранилище остаётся
  источником истины. Неизвестный `id` — `StorageError`.
- `Storage.create_item(category_id, title="Пункт")` добавляет пункт в конец
  своей категории (`position = count`, `is_checked = 0`), материализует порядок
  пунктов категории и возвращает `domain.Item`; название нормализуется доменом
  (пустое → «Пункт»). Неизвестный `category_id` — `StorageError`, БД не меняется
  (пункт без категории не существует).
- `Storage.set_item_title(item_id, title)` сохраняет название пункта и
  возвращает нормализованное значение — так же, как `set_category_title()`
  у категории.
- `Storage.move_item(item_id, category_id, new_position)` переставляет пункт —
  в его категории или в другую (`UPDATE category_id`), материализует порядок
  пунктов прежней и новой категории и возвращает порядок затронутых категорий
  (`dict[int, list[Item]]`, одна или две записи). Позиция — как у
  `move_category`: индекс в списке после удаления перемещаемого пункта, значение
  вне диапазона подрезается. Неизвестный пункт или категория — `StorageError`,
  БД при этом не меняется (транзакция откатывается).
- `Storage.list_items()` возвращает все пункты одним запросом с JOIN на
  категории: порядок — как у категорий на экране, внутри категории — по
  `position`. Пункты раскладываются по категориям в `mount()`, N+1 запросов нет.
  `list_categories()` и `list_items()` вызываются из `asyncio.to_thread`.

### Запуск внутри песочницы DSH
Программы, запускаемые из папки проекта, не могут писать в профиль пользователя,
а Flet кэширует десктопный клиент в `~/.flet`. Поэтому профиль подменяется
на каталог проекта:

```powershell
$env:USERPROFILE = "$PWD\.flet\home"
.venv\Scripts\flet.exe run
```

Первый такой запуск скачивает клиент Flet (~100 МБ) в `.flet/home`; каталог
`.flet/` в git не попадает. Проверено: окно приложения открывается, создание
категории сохраняется в `.flet/storage/data/app.db` и восстанавливается при
следующем запуске. Этот файл — dev-данные, его можно удалить.

`flet run` останавливается не сразу: после `Stop-Process flet` дочерние
`python.exe` ещё держат `app.db` и pid-файлы в корне проекта. Пока они живы,
файл удалить нельзя; процессы ищутся по пути
`.venv\Scripts\python.exe` / `.python\3.12\python.exe` от корня проекта.

## Запуск на смартфоне по USB

Инструмент — `tools\run_on_device.cmd` (обёртка над `tools\run_on_device.ps1`),
внутри — `flet debug android` (`flutter run --no-resident`): сборка debug-APK,
установка на телефон через adb, запуск. Wi-Fi и приложение Flet из Play Store
не нужны. Скрипт сам проверяет по `adb shell pidof`, что приложение запустилось,
печатает «Готово: …» и завершается с кодом 0 — ждать окончания процесса не нужно.

```powershell
# toolchain и список подключённых устройств
cmd /c "tools\run_on_device.cmd -SetupOnly"

# сборка, установка и запуск (ID устройства — из вывода выше)
cmd /c "tools\run_on_device.cmd -DeviceId 3B161E00W5600000"

# то же, но остаться подключённым: логи и hot reload
cmd /c "tools\run_on_device.cmd -DeviceId 3B161E00W5600000 -Attach"
```

Запускать нужно с полным доступом (`danger-full-access`): Flutter и Gradle
создают дочерние процессы (adb, java, git) с пайпами, а ограниченная песочница
это запрещает — сборка падает с `CreateFile failed 5` или
`ProcessException: Отказано в доступе`.

Проверено на CPH2747 (Android 16, arm64-v8a): первый запуск с нуля — около
40 минут (≈10 минут toolchain и ≈27 минут `assembleDebug`: NDK, CMake и
недостающие пакеты SDK доезжают в процессе). При готовом toolchain — 30–40
секунд: инкрементальная `assembleDebug` ≈16 с, установка ≈8 с. Пакет
приложения — `com.example.my_checklist` (из заглушки `org = "com.example"`;
её надо заменить до сборки релизного APK).

Приложение после запуска остаётся работать на телефоне — его можно закрыть
через `adb shell am force-stop com.example.my_checklist`. Повторная проверка без
пересборки: `adb shell am start -W -n com.example.my_checklist/.MainActivity`
(меньше секунды). В режиме `-Attach` процесс `flutter run` остаётся
подключённым; если телефон заблокируется или погаснет экран, связь теряется
(`Lost connection to device`) и приложение закрывается.

Жесты для проверки на устройстве удобнее подавать `input draganddrop`: у
`input motionevent` каждый вызов — отдельный процесс, и `UP` не доходит до
распознавателя (в логе нет `on_long_press_end`, пункт остаётся «поднятым»),
поэтому такой жест годится только для проверки самой прокрутки — отпускание
приходится делать вручную. `draganddrop` начинает движение сразу, поэтому
быстрый жест на длинную дистанцию долгим нажатием не становится: за 500 мс до
срабатывания таймера палец успевает уйти дальше порога касания, и жест
получается обычной прокруткой (в логе нет ни `on_long_press_start`, ни
`on_long_press`). Чтобы пункт действительно «поднялся», жест должен начинаться
медленно — например, диагональ на 30 с: первые 500 мс дают ~10 физических px
при пороге касания 28.

Строка, ушедшая из кеша списка, теряет жест — найдено и исправлено на CPH2747
(тот же набор данных). Воспроизведение: долгое нажатие по «Пункт 1.2», палец
уводится к нижней границе и держится там, пока проход не доедет до конца списка
(`on_scroll` с `pixels` 1296.2857 = `max_scroll_extent`, затем `end`). После
этого клиент **перестаёт присылать** `on_long_press_move_update`: движение пальца
к середине экрана и обратно не даёт в логе ни одного события, кадры экрана
побайтово совпадают (прокси замер), а свайп по списку возвращался к его концу —
событие `end` от прокрутки пальцем снова заказывало проход к краю. Контрольный
опыт отделил причину от «начала анимации»: короткий проход (список уже почти
в конце, строка остаётся в видимой области) жест не рвёт — после `end` приходят
`on_long_press_move_update`, а уход из зоны заказывает `scroll_to({delta: 0})`.
То есть жест теряется ровно тогда, когда строка уходит за пределы кеша ленивого
списка, а не когда начинается автопрокрутка.

После исправления (`cache_extent` на время перетаскивания) тот же жест: проход
доходит до конца (`end`, `pixels` 1296.2857), и сразу после него приходят
`on_long_press_move_update` с новыми координатами пальца (сначала `y` 600, затем
485.7), уход из зоны заказывает `scroll_to({delta: 0})`, а прокси едет за
пальцем — кадры на каждой точке разные. Отпускание после долгого прохода тоже
доходит: жест `input draganddrop 434 2500 434 2700 5000` (палец почти сразу
входит в зону, отпускание — у нижней границы экрана уже после дохода до конца)

### Toolchain
Первый запуск разворачивает всё в `.flet\home` (а не в профиль пользователя —
туда песочница писать не даёт):

| Компонент | Путь | Версия |
|---|---|---|
| Flutter SDK | `.flet\home\flutter\3.47.9` | 3.47.9 (пин из flet) |
| JDK | `.flet\home\java\17.0.13+11` | 17.0.13 |
| Android SDK | `.flet\home\Android\sdk` | platform-tools, platforms;android-34/35/36, build-tools;34.0.0 и 35.0.0, CMake 3.22.1, NDK 28.2 (недостающие пакеты доставляет Gradle при первой сборке) |
| Кэши | `.flet\home\.gradle`, `.flet\home\.pub-cache` | — |

Особенности окружения, без которых сборка не идёт:

- **Flutter ставится не flet, а скриптом.** Встроенный распаковщик flet
  (Python `zipfile`) падает на архиве Flutter: в нём есть файлы, которые вместе
  с каталогом проекта дают 262 символа, а Windows ограничивает путь 260.
  Скрипт качает архив `curl.exe` и распаковывает `tar.exe` (длинные пути умеет),
  после чего flet находит SDK на месте и не переустанавливает его.
- **`JAVA_TOOL_OPTIONS=-Duser.home=<.flet\home>`.** JVM берёт `user.home` из
  профиля Windows, а не из `USERPROFILE`, поэтому без этого `sdkmanager` пишет
  в `C:\Users\<user>\.android` и не может скачать даже списки пакетов.
- **`PYTHONIOENCODING=utf-8`.** Иначе flet падает с `UnicodeEncodeError:
  'charmap' codec` на первом же выводе pip (консоль здесь cp1251).
- **Шаблон Flutter-проекта чистится от desktop-платформ.** В шаблоне
  `flet-build-template` есть `windows/` и `linux/`; Flutter создаёт для них
  симлинки на плагины, а окружение агента их создавать не может
  (`WinError 1314`; «Режим разработчика» Windows не помогает — процесс работает
  с пониженными правами). Проект Android-only, поэтому скрипт один раз вырезает
  эти каталоги из кэша шаблона
  (`.flet\home\.flet\cache\build-template\v1.1.2`) и ставит рядом маркер
  `android-only.marker`.
- **Архивы Python для Android берутся из локального кэша.** Плагин
  `serious_python_android` на каждой сборке делает ETag-запрос к GitHub
  (`downloadDistArchive_<abi>`) и при ответе `502 Bad Gateway` валит сборку, хотя
  архивы уже лежат в `.flet\home\.flet\cache\python-build`. Скрипт идемпотентно
  патчит `build.gradle.kts` плагина в кэше pub: если файл уже скачан, задача
  пропускается (`StopExecutionException`). Если архива нет, он скачается как обычно.

### Сеть
Индекс колёс Flet `https://pypi.flet.dev` нужен при упаковке Python-кода
(`flet debug` вызывает pip): для Android единственная нативная зависимость Flet —
`msgpack`, её Android-колесо есть только там. Без VPN/прокси pip падает с
`No matching distribution found for msgpack>=1.1.0`. GitHub нужен только за
архивами `python-build`, и то лишь пока их нет в локальном кэше.

### Ограничения песочницы DSH (Windows)
В ограниченном режиме (workspace-write) каталоги, созданные с правами `0700`
(`tempfile.mkdtemp`, `Path.mkdir(mode=0o700)` внутри pytest), становятся
недоступны процессу. С полным доступом нужно выполнять:
- установку и обновление пакетов через pip;
- тесты, использующие `tmp_path` (простые тесты без временных каталогов
  проходят и в ограниченном режиме).

Отдельное ограничение действует даже при полном доступе: программы, запускаемые
из папки проекта (`.venv\Scripts\python.exe`, `.python\3.12\python.exe`),
не могут писать в профиль пользователя `C:\Users\MineF`. Поэтому `flet run`
запускается с подменённым `USERPROFILE` (см. «Команды»), а запуск на телефоне
подменяет все каталоги инструментов — см. «Запуск на смартфоне по USB».

Сборка под Android требует полного доступа и по другой причине: в ограниченном
режиме Dart (движок Flutter) не может запускать дочерние процессы через пайпы —
`git`, `java`, `adb` падают с `CreateFile failed 5` и
`ProcessException: Отказано в доступе`.

Из-за ограничения с `0700` в `pyproject.toml` отключён кэш pytest
(`addopts = "-p no:cacheprovider"`): иначе каждый запуск создаёт в корне
недоступные каталоги `pytest-cache-files-*`. Тесты без `tmp_path` идут
в обычном режиме.

Тесты хранилища используют `tmp_path`, поэтому запускаются только с полным
доступом. Их временный каталог (`pytest-of-*`) может появиться в корне проекта
с правами `0700` — после прогона его нужно удалить тоже с полным доступом.
Чтобы он не появлялся в корне, можно задать `TEMP`/`TMP` внутри `.tmp/`:

```powershell
$env:TEMP = "$PWD\.tmp\pytest"; $env:TMP = $env:TEMP
New-Item -ItemType Directory -Force $env:TEMP | Out-Null
.venv\Scripts\python.exe -m pytest
```

### Git в песочнице DSH
- Штатный TLS-бэкенд git (schannel) в песочнице падает с
  `SEC_E_NO_CREDENTIALS`, поэтому в локальном конфиге репозитория выставлен
  `http.sslBackend=openssl` (в git не коммитится).
- `git push` требует полного доступа: git-credential-manager не работает,
  пока песочница запрещает pipes.
