# Краткое описание
## Цель
Сохранять категории, пункты, их порядок и отметки локально на устройстве, чтобы состояние приложения не терялось между запусками

## Список функций
- Данные хранятся локально в SQLite
- Хранятся категории, пункты, их порядок и отметки
- Порядок категорий и порядок пунктов внутри категории сохраняются после перезапуска
- При удалении категории удаляются все её пункты
- Схема БД версионируется и мигрируется
- Приложение работает без сети, аккаунта и синхронизации

# Подробности
## Общие принципы
- Хранилище — единственный источник достоверных данных: после перезапуска состояние восстанавливается только из него
- Хранилище не придумывает значения: заголовки и дефолтные имена нормализуются доменом до записи (см. [feature-category.md](feature-category.md), [feature-item.md](feature-item.md))
- Приложение — единственный писатель БД: один процесс, один пользователь, блокировки между процессами не проектируются
- Хранилище не знает про UI: не хранит выделение, прокрутку, режим переименования и состояние перетаскивания

## Что хранится

### Категория
| Поле | Тип | Правила |
|---|---|---|
| `id` | целое | первичный ключ, не переиспользуется после удаления |
| `title` | текст | не пустой после `trim`; дефолт подставляет домен («Категория») |
| `position` | целое | позиция среди всех категорий, `0..n-1` |

### Пункт
| Поле | Тип | Правила |
|---|---|---|
| `id` | целое | первичный ключ, не переиспользуется после удаления |
| `category_id` | целое | ссылка на категорию, `NOT NULL`: пункт без категории не существует |
| `title` | текст | не пустой после `trim`; дефолт подставляет домен («Пункт») |
| `is_checked` | целое | `0` или `1`; при создании `0` |
| `position` | целое | позиция внутри своей категории, `0..n-1` |

Служебное:
- `meta(key, value)` — служебные пары, в том числе `schema_version`

## Что не хранится
- Выделенная категория или пункт
- Позиция прокрутки
- Режим переименования и текущий ввод до коммита
- Состояние перетаскивания
- Метки времени: в спеке нет функций, которым они нужны

## Схема БД
Версия схемы: `1`.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS categories (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    title    TEXT    NOT NULL CHECK (length(trim(title)) > 0),
    position INTEGER NOT NULL CHECK (position >= 0)
);

CREATE TABLE IF NOT EXISTS items (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    category_id INTEGER NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
    title       TEXT    NOT NULL CHECK (length(trim(title)) > 0),
    is_checked  INTEGER NOT NULL DEFAULT 0 CHECK (is_checked IN (0, 1)),
    position    INTEGER NOT NULL CHECK (position >= 0)
);

CREATE INDEX IF NOT EXISTS idx_items_category_position
    ON items(category_id, position);
```

Примечания:
- `AUTOINCREMENT` — чтобы `id` удалённых строк не переиспользовались (иначе старые ссылки в памяти UI могут указывать на чужую запись)
- `ON DELETE CASCADE` работает только при `PRAGMA foreign_keys = ON`, поэтому прагма включается **на каждом соединении**, а не один раз при создании файла
- `UNIQUE` на `position` намеренно не ставится: переиндексация делает уникальность транзиентно нарушенной. Уникальность обеспечивается операциями и проверяется при загрузке

## Правила порядка
- `position` — целое, без пропусков, уникально в пределах контейнера (категории — весь список, пункты — своя категория)
- После любой изменяющей операции позиции затронутого контейнера (контейнеров) **материализуются заново**: `0..n-1` в новом порядке. Это устраняет дыры и дубли и делает операции идемпотентными
- Перенос пункта в другую категорию материализует позиции **двух** контейнеров: старой и новой категории
- Порядок чтения: `ORDER BY position ASC, id ASC` (второй ключ — только для детерминированности при нарушенном инварианте)

## Операции
| Операция | Действие | Затрагиваемые контейнеры |
|---|---|---|
| Создать категорию | `INSERT` с `position = count`, затем материализация | категории |
| Переименовать категорию | `UPDATE title` | — |
| Переместить категорию | обновить порядок, затем материализация | категории |
| Удалить категорию | `DELETE FROM categories WHERE id = ?` (пункты удаляются каскадом) | категории |
| Создать пункт | `INSERT` с `category_id`, `position = count`, `is_checked = 0`, затем материализация | пункты категории |
| Переименовать пункт | `UPDATE title` | — |
| Переключить отметку | `UPDATE is_checked` (значение передаётся явно, не инвертируется в SQL) | — |
| Переместить пункт внутри категории | обновить порядок, затем материализация | пункты категории |
| Переместить пункт в другую категорию | `UPDATE category_id`, затем материализация | пункты старой и новой категории |
| Удалить пункт | `DELETE FROM items WHERE id = ?`, затем материализация | пункты категории |

Пункты удалённой категории отдельно не удаляются: это делает каскад.

## Транзакции и запись
- Одна пользовательская операция = одна транзакция: `BEGIN` → изменения → `COMMIT`
- Коммит выполняется **до** обновления UI: если запись не удалась, состояние интерфейса не меняется
- При любой ошибке — `rollback`, операция считается неуспешной, UI показывает ошибку и остаётся в прежнем состоянии
- Операции с БД не выполняются в потоке отрисовки: обёрнуты в `asyncio.to_thread` (Flet-приложение асинхронное), иначе интерфейс подтормаживает
- При инициализации: `PRAGMA journal_mode = WAL` (сохраняется в файле), `PRAGMA busy_timeout = 5000`
- Чтение: один запрос с `JOIN`/`ORDER BY`, без N+1; пагинация не нужна — список загружается целиком

## Расположение и инициализация
- Файл `app.db` лежит в приватном каталоге данных приложения (на Android — внутреннее хранилище приложения), путь получается от платформы и не хардкодится
- Файл БД не кладётся в ресурсы приложения и не пишется в общедоступные каталоги
- Первый запуск: создаётся файл, применяется схема v1, список категорий пустой (демо-данные не создаются)
- Последующие запуски: применяются недостающие миграции, затем загрузка данных

## Миграции
- Текущая версия схемы хранится в `meta` под ключом `schema_version`
- Миграции применяются последовательно от текущей версии к актуальной, каждая — в отдельной транзакции
- Понижение версии схемы не поддерживается: при `schema_version` больше ожидаемой приложение не стартует и сообщает об ошибке
- Изменения схемы только добавляют таблицы/колонки/индексы; удаление и переименование колонок — через новую таблицу и `INSERT ... SELECT`

## Устойчивость и ошибки
- Битый или нечитаемый файл БД: переименовывается в `app.db.corrupt-<timestamp>`, создаётся пустая БД, пользователю показывается сообщение о потере данных
- Ошибка записи (нет места, файл только для чтения): транзакция откатывается, данные в памяти остаются прежними
- Проверка целостности порядка при загрузке: при дублях или пропусках в `position` порядок нормализуется и сохраняется
- Ограничений на объём нет, расчётный максимум — сотни категорий и тысячи пунктов

## Сценарии приёмки
1. Дано: пустая БД. Когда пользователь создаёт категорию «Работа». Тогда после перезапуска приложения категория «Работа» отображается одна и на первой позиции.
2. Дано: в категории «Работа» три пункта. Когда пользователь меняет их порядок и перезапускает приложение. Тогда порядок пунктов сохраняется.
3. Дано: у пункта включена отметка. Когда пользователь перезапускает приложение. Тогда отметка сохраняется, пункт отображается отмеченным.
4. Дано: выделен пункт. Когда пользователь перезапускает приложение. Тогда ничего не выделено.
5. Дано: категория с двумя пунктами. Когда пользователь удаляет категорию. Тогда после перезапуска нет ни категории, ни её пунктов, а порядок остальных категорий не изменился.
6. Дано: два пункта в категории «Дом». Когда пользователь переносит пункт в категорию «Работа» и перезапускает приложение. Тогда пункт принадлежит «Работе» и стоит на своей позиции в ней.
7. Дано: БД со схемой v1. Когда приложение запускается после обновления с миграцией v2. Тогда данные на месте и `schema_version = 2`.
8. Дано: файл БД повреждён. Когда приложение запускается. Тогда оно не падает, создаёт пустую БД и сообщает о потере данных.
9. Дано: пользователь добавляет пункт и не вводит название. Когда ввод завершается. Тогда в БД сохраняется пункт с названием «Пункт», и после перезапуска он называется так же.

## Не входит
- Синхронизация, резервное копирование, экспорт/импорт
- Шифрование БД
- Поиск, фильтрация, теги
- Хранение истории изменений
